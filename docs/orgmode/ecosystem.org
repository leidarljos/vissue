#+title: Ecosystem
#+options: toc:nil num:nil

Three tools read the same bytes. Nothing synchronises them, because there is
only one copy: the Org file.

#+begin_src
                 Software/<project>/issues.org
                    |          |          |
             vissue |    Emacs |    orgaw |
        work items  |  agenda, |  time and
        and the DAG |    tags, |  evidence
                    |  id links|
#+end_src

* Emacs

Emacs is a client of the corpus rather than of the command. A tracker is an
ordinary Org file, so the agenda, tag search, and =id:= links work against it
with nothing installed.

That holds because vissue writes what Org reads: deadlines and scheduled
dates on the planning line under a heading, tags in the heading's own tag run
aligned to =org-tags-column=, =#+CATEGORY:= naming the project, and =:ID:=
that =org-id= resolves. =org-lint= finds nothing to say about a file vissue
wrote.

The traffic goes both ways. =C-c C-d=, =C-c C-s=, =C-c C-q=, and marking an
issue DONE under =org-log-done= all work on an issue heading, and vissue
reads back what they write.

#+begin_src elisp
;; Put the tracker in the agenda by hand:
(setq org-agenda-files (directory-files-recursively "~/notes/Software" "issues\\.org\\'"))
(org-id-update-id-locations org-agenda-files)
#+end_src

** vissue.el

[[https://github.com/HaoZeke/vissue.el][vissue.el]] is the optional convenience layer, not a
requirement.

- =M-x vissue-add-to-agenda= puts every tracker file on =org-agenda-files=
  and refreshes =org-id= locations. After it, =M-x org-agenda= lists issues
  by deadline and =id:= links to issues resolve.
- =M-x vissue-list= shows the ready set; =RET= opens an issue, =c= claims it,
  =g= re-reads.
- =M-x vissue-related-at-point= shows the explained neighbourhood of the
  issue at point.

** Checking the two agree

=tests/org_interop.sh= drives real Emacs over a tracker: =org-lint= finds
nothing, the agenda shows both dates and labels rows by project, tag search
matches, =org-id= resolves, then Emacs performs the destructive edits and
vissue reads the result back unchanged.

#+begin_src console
$ bash tests/org_interop.sh ./target/release/vissue
#+end_src

* orgaw

[[https://github.com/HaoZeke/orgaw][orgaw]] records intentional time and evidence against
the same headings. vissue manages the work items; orgaw puts CLOCK entries
under them. The projects install independently and meet at the file and at
the command-line protocol.

#+begin_src console
$ cargo install vissue-cli
$ cargo install orgaw
$ export ISSUE_ROOT=/path/to/notes
$ vissue ready
$ orgaw issues
$ orgaw in project-id
$ orgaw out
#+end_src

Clocking in claims the issue through vissue, so the two views agree on who
holds what.

** What the two agree on

- *The lock.* Both serialise on =issues.org.lock=. Without that, a vissue
  mutation that had read the file but not yet written it would overwrite a
  CLOCK appended in between, and nothing would report it.
- *The planning line.* A =:LOGBOOK:= drawer goes below the planning line and
  the property drawer. A stamp that stops touching its heading stops being a
  stamp.
- *Opaque logbook lines.* vissue keeps CLOCK entries and orgaw's own metadata
  lines verbatim across a rewrite, and carries them in the export as =raw=.

** Checking that too

=tests/orgaw_interop.sh= runs orgaw against a tracker vissue wrote and
asserts both directions. It skips when orgaw is absent.

#+begin_src console
$ bash tests/orgaw_interop.sh ./target/release/vissue /path/to/orgaw
#+end_src

orgaw ships the mirror image as =tests/vissue-orgaw-integration.sh=.

* Version compatibility

The three move together. A tracker written by a current vissue is not
readable by 0.1.0, which fails on the planning line, and an orgaw older than
the planning-line fix inserts its drawer above the stamp and breaks the file
for every reader. Upgrade them as a set.
